# Правила работы с проектом PricePulse

## 1. Архитектура и внедрение зависимостей (DI)
- Проект использует **гексагональную архитектуру (DDD)** и библиотеку `samber/do` для внедрения зависимостей.
- При создании новых компонентов (Command, Query, Repository, Client, Worker) **ОБЯЗАТЕЛЬНО** добавлять их провайдеры (`do.Lazy` / `do.Provide`) в соответствующий файл `package.go` в той же директории.
- Не забывать импортировать эти `Package` в `cmd/main.go` и производить инициализацию контейнера.

## 2. Кодогенерация и чистота
- После использования утилит для редактирования кода (`sed`, `patch` и т.д.) **ОБЯЗАТЕЛЬНО** удалять все временные артефакты (файлы `*.patch`, `*.orig`). В рабочей директории не должно оставаться мусора.
- Не создавать дубликаты существующих структур (например, если уже есть `type Handler struct`, новые HTTP-методы нужно привязывать к нему, а не создавать `Handlers`).
- Если создается новый сервис (модуль), его `cmd/main.go` должен быть полностью работоспособным: с парсингом конфигов, инициализацией БД/инфраструктуры, сборкой DI-контейнера и запуском серверов. Не оставлять `main.go` пустым.

## 3. Самопроверка
- Всегда запускать `go mod tidy` и `go build ./...` после добавления нового кода.

## 4. Тестирование и Моки
- Для генерации моков **всегда использовать утилиту `vektra/mockery`**. Рукописные стабы (stubs) запрещены.
- Конфигурация для mockery должна лежать в `.mockery.yaml` на уровне тестируемого модуля (например, в `catalog/`).
- Для получения сгенерированного мока использовать конструктор вида `mocks.NewMock<InterfaceName>(t)`, как это заведено в mockery v2+.
- Все DI-пакеты (`package.go`) должны иметь unit-тесты (например `package_test.go`), где зависимости подменяются сгенерированными моками.
