# Дизайн-документ: Сопоставление позиций чека и предложение новых товаров

## 1. Описание задачи (Business Context)
После загрузки чека в систему пользователю необходимо сопоставить купленные позиции (сырые строки из чека) с глобальными товарами платформы. 
Если подходящего товара нет, пользователь может предложить новый товар. Предложенные товары проходят модерацию: до момента подтверждения администратором они имеют статус черновика (Draft) и видны только автору и администраторам.

## 2. Затронутые модули и компоненты
Для реализации функционала система будет расширена. Затронуты следующие области:
1. **Новый модуль `catalog` (Каталог)** — отдельный микросервис (Go-модуль) для управления товарами платформы.
2. **Модуль `receipts` (Чеки)** — обновление домена и БД для хранения связи между позицией в чеке и товаром.
3. **Модуль `auth` (Авторизация)** — расширение модели аккаунта для поддержки ролей.
4. **Инфраструктура:** 
   - **Elasticsearch (ES)** — для полнотекстового поиска и скоринга.
   - **API Gateway** — для проверки ролей на основе JWT (за рамками кода сервисов).

---

## 3. Архитектурные решения (ADR)

### 3.1. Elasticsearch для поиска товаров
**Решение:** Поиск подходящих товаров будет осуществляться через Elasticsearch (а не SQL-запросами к PostgreSQL).
**Причина:** Необходим быстрый полнотекстовый поиск (Fuzzy matching) и сортировка по релевантности (score) для выдачи оптимальных подсказок пользователю.

### 3.2. Синхронизация PostgreSQL -> Elasticsearch (Outbox Pattern)
**Решение:** Для синхронизации данных между основным хранилищем (PostgreSQL) и поисковым индексом (ES) будет использоваться паттерн **Transactional Outbox**.
**Причина:** Обеспечение консистентности. При создании/изменении товара в транзакции БД также создается запись в таблице `outbox_events`. Отдельный фоновый воркер асинхронно читает события и обновляет индекс в ES. Это исключает потерю данных в индексе при временной недоступности ES.

### 3.3. Взаимодействие сервисов (gRPC)
**Решение:** Сервис `receipts` будет общаться с сервисом `catalog` по **gRPC**.
**Причина:** При привязке `ProductID` к `ReceiptItem` сервису чеков необходимо валидировать, существует ли такой товар. gRPC обеспечит быструю, строго типизированную и легковесную синхронную проверку (например, метод `CheckProductExists`).

### 3.4. Видимость предложенных товаров
**Решение:** Хранение связи `Product -> Creator` (кто предложил) в реляционной БД реализовано через отдельную связующую таблицу `product_proposals`. В **Elasticsearch** поле `owner_id` будет денормализовано и добавлено прямо в документ товара.
**Причина:** Денормализация в ES необходима для быстрого применения фильтра безопасности при поиске: `Status = 'Approved' OR (Status = 'Draft' AND owner_id = :current_user_id)`.

## 4. Модель данных

### Модуль `auth`
- **Сущность `Account`:** добавляется поле `Role string` (значения: `user`, `admin`).
- **JWT payload:** в claims токена добавляется поле `role`.

### Модуль `catalog` (PostgreSQL)
- **Таблица `products`:** `id` (uuid), `name` (string), `status` (enum: `draft`, `approved`, `rejected`), `created_at`, `updated_at`.
- **Таблица `product_proposals`:** `product_id` (uuid, fk), `account_id` (uuid - автор предложения), `created_at`.
- **Таблица `outbox_events`:** `id`, `entity_type`, `entity_id`, `payload`, `status`, `created_at`.

### Модуль `catalog` (Elasticsearch Index `products`)
```json
{
  "id": "uuid",
  "name": "string (text with analyzers)",
  "status": "string (keyword)",
  "owner_id": "uuid (keyword)"
}
```

### Модуль `receipts`
- **Сущность `ReceiptItem`:** добавляется опциональное поле `ProductID *uuid.UUID`.
- **Таблица `receipt_items`:** добавляется колонка `product_id` (soft foreign key, так как товар лежит в другой БД).

## 5. Основные сценарии (Flows)

### 1. Поиск подходящего товара (Пользователь)
1. Клиент запрашивает: `GET /catalog/search?q=Молоко&limit=10`.
2. Запрос проходит через API Gateway (добавляется `X-User-Id` из JWT).
3. Сервис `catalog` формирует запрос к ES, фильтруя товары по статусу (`Approved` ИЛИ (`Draft` + совпадает `owner_id`)).
4. Возвращается отсортированный по score список.

### 2. Предложение нового товара (Пользователь)
1. Клиент отправляет: `POST /catalog/propose {"name": "Новое молоко"}`.
2. В PostgreSQL стартует транзакция:
   - Вставляется запись в `products` (status: `draft`).
   - Вставляется запись в `product_proposals` (с `account_id`).
   - Вставляется событие `ProductCreated` в `outbox_events`.
3. Фоновый воркер перехватывает событие и индексирует документ в ES (включая `owner_id`).

### 3. Сопоставление позиции чека с товаром (Пользователь)
1. Клиент отправляет запрос в модуль `receipts`: `PATCH /receipts/{id}/items/{item_id} {"product_id": "uuid"}`.
2. Сервис `receipts` делает **gRPC** вызов к сервису `catalog`: `CheckProductExists(product_id, current_user_id)`.
3. `catalog` отвечает `true` (товар существует, активен или предложен этим же юзером).
4. `receipts` сохраняет `ProductID` в свою БД.

### 4. Подтверждение товара (Администратор)
1. Админ вызывает: `PUT /catalog/admin/products/{id}/approve` (API Gateway пускает только юзеров с `role=admin`).
2. В БД `products` статус меняется на `approved`.
3. Через Outbox генерируется событие обновления.
4. В ES статус документа обновляется, после чего товар становится доступен в поиске для всех пользователей.

## 6. Риски и "Неизвестные" факторы
- **Коллизии при добавлении товаров:** Разные пользователи могут параллельно предлагать один и тот же товар (например, с небольшими опечатками). В будущем потребуется внедрить механизм слияния (Merge) дубликатов и проверки похожих `draft` товаров на стороне администратора.
- **Инфраструктурная сложность:** Появление gRPC, Outbox worker и Elasticsearch значительно усложняет локальную разработку. Потребуется обновление `docker-compose.yml` и написание скриптов для накатки миграций/индексов ES.
